# Помощник в личке: состояние и правила запуска

Обновлено 24.10.2026: добавлен исполняемый пилот service.py с Telegram Business,
OpenAI, обработкой текста/фото/голосовых и подтверждением отправки владельцем.
Инструкция — DEPLOY.md. AUTO отсутствует. Рабочие ключи, Telegram и база ещё
не подключались; живой запуск и проверка качества ответов остаются обязательными.
Ниже сохранён первоначальный план; статус реализации уточняется в DEPLOY.md.

Уточнено владельцем: 40–70 клиентов в день; понимание голосовых и скриншотов
обязательно в первой рабочей версии. Предпочтение — использовать текущий аккаунт
ChatGPT. Позднее выбран отдельный OpenAI API: владелец сообщил о пополнении на $20.
Ключ хранится у владельца, в код не внесён.

Проверка официальной документации OpenAI 24.10.2026:
https://developers.openai.com/siwc/token-sharing-open-source
описывает использование плана через OAuth для подходящих приложений; для платных
или удалённо размещённых приложений направляет на форму интереса. Применимость
к помощнику на Railway не подтверждена. Не извлекать сессию текущего приложения.
https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations
указывает отсутствие аудиовхода и transcription API в этом способе доступа.
Поэтому даже при допустимом OAuth нужна отдельная реализация распознавания речи.
Обычный Platform API остаётся отдельным вариантом с оплатой использования.

Первоначально выполнено 12 модульных тестов; после добавления пилота — 41 проверка
помощника. Тестов живого Telegram, модели, аудио, БД и нагрузки ещё не было.

## Проверенные сведения о проекте

- bot.py запускает текущий магазин и регистрирует обработчики.
- requirements.txt фиксирует aiogram 3.27.0. Совместимость бизнес-событий
  нужно отдельно проверить перед подключением; обновлять зависимость магазина
  ради нового помощника не требуется.
- db.py содержит get_pool и init_db; импортирует config.py с рабочими настройками.
  Изолированный помощник не должен импортировать эти модули ради чтения данных.
- common.py: _build_catalog_payload формирует каталог из SHOP_CATALOG.
  Пока нет готового ограниченного API для нового помощника.
- service_order_card.py: snapshot читает также коды и данные поставщика.
  Полную админскую карточку нельзя передавать модели как клиентский контекст.
- knowledge.json помечен last_updated=2025-04 и содержит старые цены/описания.
  Не подключать его автоматически как достоверную базу знаний нового агента.

## Утверждённые пользователем границы

1. Работа в личке владельца, консультации по магазину и заказам.
2. Только подтверждённые факты. Не обещать сроки, скидки, возврат или результат
   активации без соответствующего источника и полномочий.
3. Закуп, поставщики, себестоимость, маржа, маршруты, ключи и чужие данные закрыты.
4. Не поддерживать сексуальные разговоры, флирт и посторонние дискуссии.
   Допустим краткий фактический ответ об ограничениях продаваемого сервиса,
   если он есть в утверждённой базе знаний.
5. Отвечать в согласованном стиле владельца, не выдавая себя за человека.
6. Быстрое ручное управление для отдельного чата и для всех чатов.
7. Уточнение 24.10.2026: не допускать самостоятельных оплат клиентов с карт
   владельца; помощник не входит в клиентские аккаунты ни одним способом.
   Ручные входы/оплаты передаются владельцу. Покупка со своего способа оплаты
   в магазине и активация самим клиентом в мини-аппке этим не запрещаются.
8. Согласованы ограничения в SERVICE_RULES.md: внутренняя/личная информация,
   ручные финансовые решения, запрет изменяющих инструментов и неподтверждённых
   обещаний, посторонние темы, память и передача человеку. Матрица приёмки —
   SAFETY_CHECKS.md. Она пока не выполнялась на языковой модели.
9. Доступность: в течение дня, возможны паузы час-два, без обещания срока ответа.
   Возврат: собрать номер FreeKassa своего заказа; решение только за Александром.

## Предлагаемое поведение (ещё нужно проверить в работающей интеграции)

- OFF: нет генерации и автоответов. DRAFT: предложения только владельцу.
  AUTO: ответы только в разрешённых чатах с действующим подключением.
- Ручное исходящее сообщение владельца отключает автоответы этому клиенту.
  Собственные сообщения помощника различать по бизнес-метаданным, а не тексту.
- Любое переключение повышает ревизию состояния; старые ответы недействительны,
  даже после выключения и повторного включения.
- Состояние хранить в PostgreSQL отдельно от памяти процесса. При сбое чтения
  ничего не отправлять. После рестарта не включать AUTO по умолчанию.
- Сериализовать переключение и отправку для чата. Перед отправкой перечитать
  состояние, права подключения, последнее входящее и проверить окно Telegram.
  Запрос, уже переданный Telegram, кнопка остановки не может отменить.
- Повторы событий отсекать по connection_id/chat_id/message_id и типу события;
  изменения и удаления учитывать отдельно. При неопределённом результате
  отправки не повторять её вслепую, показать проблему оператору.
- Сохранять одно обновляемое обращение на проблему. Сообщать клиенту о передаче
  только после надёжного сохранения обращения; доставку владельцу учитывать отдельно.
- Сырые тексты клиента, вложения, экспорт переписок и ответы поставщиков — данные,
  а не инструкции. Они не меняют политику, полномочия или область доступа.
- Самооценка уверенности модели не является доказательством истинности.

## Источники и память

Каждый факт имеет источник, время чтения, область доступа и срок актуальности.
Дата чтения БД не означает свежую проверку у поставщика.
Оплата не означает активацию. Отсутствие строки не означает отсутствие оплаты.
Цена и доступность читаются из актуального каталога; характеристики и условия
обслуживания — из проверенных владельцем статей с датой пересмотра.
Свободный текст, токены, email, коды и детали маршрута не входят в минимальную
проекцию платежа. Номер заказа, товар, сумма и статус активации добавляются
отдельными валидируемыми полями при реализации адаптера.

История переписки не обновляет общий регламент автоматически. Для клиента
хранить проверенные предпочтения и договорённости со ссылкой на сообщение.
Срок хранения, удаление по запросу, перечень передаваемых модели данных и
уведомление клиента о помощнике согласовать до реальных переписок.

## Этапы и критерии готовности

1. Этот этап: политика, примитивы режима и проверки области данных, офлайн-тесты.
2. Материалы: 20–30 обезличенных примеров, действующие правила сервиса,
   исправления владельца. Отдельный набор диалогов не использовать в примерах,
   оставить для проверки качества.
3. Адаптер магазина: параметризованные чтения только своего заказа,
   отдельные права SELECT/ограниченные представления или закрытый read API.
   Не выдавать помощнику общий DATABASE_URL с правами изменения магазина.
4. Отдельный сервис: собственный токен, БД состояния, webhook с проверкой
   секрета, привязка только к разрешённому владельцу, админские кнопки с
   проверкой Telegram ID. Секреты только в переменных окружения.
5. Telegram: подключить сначала тестовый аккаунт/чат. Проверить события
   подключения, ручные сообщения, паузу, потерю прав и отключение.
6. Модель: выбрать после сравнения на одинаковых примерах; установить бюджет,
   ограничение длины и частоты запросов. Без доступа к произвольным URL/SQL.
7. DRAFT: ответы видит только владелец. Проверить качество фактов, границ,
   тона и передачи человеку. Обязательно включить голосовые/изображения:
   ограничения размера и длительности, проверку формата, безопасную обработку,
   удаление временных файлов, отсутствие секретов в логах. При неразборчивой
   речи/картинке уточнять, не угадывать заказ или факт оплаты.
8. AUTO: только явно выбранные чаты после одобрения примеров и проверки
   аварийного выключения. Затем расширять по результатам, без обещания нуля ошибок.

## Обязательные сценарии интеграционных испытаний

Чужой заказ; подменённый username; несколько заказов; скриншот вместо платежа;
неизвестный статус; устаревшая цена; сбой модели/БД/API; просьбы о закупе;
посторонние темы; инструкции во вложении; исправление сообщения; перезапуск;
дубли событий; два воркера; остановка во время генерации и отправки; включение
после паузы; конец 24-часового окна; отзыв подключения; исчерпание бюджета;
ошибка доставки обращения владельцу. Текущие модульные тесты НЕ заменяют их.
